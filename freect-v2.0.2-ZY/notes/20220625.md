# FreeCT Has a C++ Problem

Hi! I'm John, the original author of the FreeCT project and the one who has attempted (albeit erratically and poorly) to keep it running over the last few years.  First, the good news is that I have just started a new position as an Assistant Professor at UCLA, and because FreeCT will likely be a cornerstone of my own research I will have significantly more time to dedicate to getting FreeCT back online and improving it.  That being said, it's likely to be a medium-term endeavor, the details of which I'd like to explain and discuss here.

**Development vs. Deployment** 

A primary goal of FreeCT was to make clinical-quality CT reconstruction available in an open-source piece of software to provide researchers with a reasonably high-performance alternative to "on-board" (i.e. on the scanner) recon, and one that was substantially more useful in high-throughput, batch-type work.  Although I think I succeeded in implementing the software and putting it out into the world for others to use, I failed in making a truly *accessible* piece of software.  In the technology space, this is the difference between software *development* and software *deployment*.

Software deployment is what makes it possible to download a pre-compiled binary applications (e.g. exe files for windows, apps for mac, packages for linux), and run them.  I'll spare you all of the details around why, but suffice it to say that software deployment (particularly with C++ software) is an enormously challenging problem and time consuming problem to solve.  Doing it well comes down to just allocating a lot of time to testing, responding to feedback, and attempting to support different computers, operation systems, *versions* of the same operating systems with slightly different libraries, computing environments, etc.  Given that FreeCT development is at this point entirely limited to me, time is the one thing I do not have.  Because of this, I chose to let FreeCT remain a tool that users would need to compile for their particular hardware and computing environment.  Looking back though, that choice has significantly limited the usability of FreeCT for all users other than the most adept and computer-saavy, and even then getting FreeCT running is a non-trivial exercise.  Hats off and thank you to those who have used it in their publications!

Some of the is inherent to CT image reconstruction (complex geometries, complex problem domain), and in that regard I think some level of investment on the part of the user is required since I will not ever be helping troubleshoot runtime issues; FreeCT will never be "plug-and-play" except for potentially some widely-available public datasets (i.e. the TCIA LDCT Projection data set).  Some addition complexity is inherent to GPU software: short of a full-time investment in FreeCT, I will never be able to write high-performance code that runs all hardware or is compiled for all possible runtime environment combinations.  Finally a substantial portion of the user-level frustration is due to C++ and some of the legacy issues that come with writing C++ software in these modern days.

**Managing Complexity in FreeCT**

I can't fundamentally reduce the complexity of CT image reconstruction on modern CT scanners, nor can I reduce the fact that FreeCT will remain GPU software, and GPUs are complicated, however I can (or at least try to) reduce the complexity of building and running FreeCT.

For one thing, I first started developing FreeCT over 10 years ago (which is hard to believe), and certain aspects of modern computer tooling has improved substantially in that time.  In particular, Docker has emerged as a powerful and reasonably accessible resource for computing environment management (a discussion of environments and why they are challenging to manage is much beyond the scope of this update, but suffice it to say that environment is the primary challenge for making FreeCT more generally available), which can help me solve one aspect of the "dependency" problem for FreeCT.  Additionally, new languages that bake dependency management into the language itself have made deployment even easier, in our case [Go](https://go.dev).  Go was only breaking into mainstream usage when I first started writing FreeCT and is now an incredibly powerful tool that I have grown to love, since it resolves many of our deployment problems by statically linking (pretty much) all of a programs dependencies. 

So I think going forward, a worthwhile effort for FreeCT is to try and make use of these tools, Docker and Go, to simply FreeCT's accessibility.

**FreeCT has a C++ Problem**

I've talked a lot about dependencies, and environments, etc. above, but really the only reason any of that matters is because FreeCT is entirely a C++ program.  For anyone who doesn't know, there are two key parts of taking source code and translating it into machine code that your computer can actually execute: *compiling* and *linking*.  Roughly speaking, compiling takes the source code in a single file, and turns it into a file of machine code that a processor would understand, something called an "object" file.  A program like FreeCT has many many source files though, and to make the program run, all of the object files need to understand how to "talk" to one another, and we also need to add some machine-readable information so that the operating system needs to know where to even start the program.  This is the function of *linking* the program.

Seems reasonable enough, but the challenge arises in that is most cases (ok, nearly all cases), there will be some resources for your program that are provided by the operating system that are *dynamically linked* to your executable.  That means that the machine code doesn't exist in your program's executable file, but rather lives in a file that the operating system will provide when you go to run your application.  These are typically things like the C++ std library, or in the case of FreeCT, 3rd-party libraries such as DCMTK, Boost, etc. (on Windows these are your .DLL files, on Mac they're .DYLIB, and on linux/unix they're .SO files). Dynamic linking essentially means that your program won't run if those libraries either don't exist, or are in a different place than the system the program was built on... or are a different version, or built for a different operating system, etc.  There's a plethora of ways that your executable can fail to find the correct shared libraries.  This is one of the reasons why you can't just copy and paste applications between linux, windows, and mac, but even sometimes can't just copy and paste a linux executable between different linux machines!

I've already gone way more into detail than I intended, but I'll just say that there, to my knowledge, are not good solutions here short of hiring a team of people to spend all of their time compiling, bundling software, and verifying that it runs on different computers and operating systems before making it publicly available; this is why release engineering and devops are entire teams unto themselves at big companies.   The tradeoff though is that if you do all of the compilation and linking on the machine you're intending to run the software on, you're end up with working software, which is why I've never offered pre-compiled version of FreeCT, instead hoping that motivated researchers could figure out the compilation process on their own.

Finally, C and C++ do not have any official build or package management or module systems, which is why things like Makefiles and CMake exist.  Although these are mature tools nowadays, they require their own level of attention and dedication to integrate into your project, and then must be maintained as a core part of the project infrastructure.  And despite their maturity, they don't work all that well to solve some of the key dependency resolution issues C++ suffers from.  Similarly, thorough testing of C++ code requires additional libraries, custom "test harnesses" that essentially become projects unto themselves, etc.

Long story short, C++ may be fast, but it's long-in-the-tooth and the development/deployment hassle these days grossly outweighs the performance gains when compared to other tools that have emerged.

**Moving towards Go**

For FreeCT, there are essentially two levels of code we can think about: (1) the GPU code that actually does the reconstruction math, and (2) everything else, such as loading files, parsing dicom, configuration information, logging, saving everything to disk, and setting up the data to be operated on by the GPU.  Ironically, pretty much all of the third party dependencies in FreeCT are in service of level (2), which means that all of the difficulty in building FreeCT could be eschewed if there were a better way to handle that stuff (i.e. *not* doing it with C++).

Lately I've been using Go extensively because it solves all of the BS I talked about in the previous section. Go's not perfect, but it fundamentally was built with addressing many of the shortcomings of C++ with respect to the build, maintenance, and deployment steps of modern software development in mind.  That choice makes it possible to write software with minimal focus on the support infrastructure, and still end up with testable, deployable, and performant software.
